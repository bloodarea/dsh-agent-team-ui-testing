# 判定范例与反例集（合成场景，非任何靶机答案）

> 目的：训练"**差异 ≠ 缺陷**"的分界，避免把所有异常现象都判成 FAIL，也避免把真实缺陷解释成设计。
> 范例全部是**合成的一般场景**；不引用任何具体被测站点、用例编号、组件名或产品文案。判定终检见 [`verdict-gate.md`](verdict-gate.md)。

## 0. 先问三个问题

任何"看起来不对"的现象，按顺序问：

1. **契约怎么说？** 需求/接口文档/页面声明是否明确允许这种表现（最终一致、幂等重放、装饰动画、静态内容、冲突提示）？
2. **用户可见结果受影响吗？** 影响可读性/金额/状态/可操作性，还是只是实现细节的差异？
3. **证据够吗？** 是否覆盖了对象、时间窗、采样规格；能否复现？

三问答完再给 verdict：**契约允许 + 无可见影响 → 不构成缺陷**；**契约不允许 + 有可见影响 + 证据充分 → 缺陷**；**契约不明/证据不足 → `INCONCLUSIVE`**。

## 1. 正常 SSE 重放 vs 重复渲染缺陷

| | 正常（不判缺陷） | 缺陷（判 FAIL） |
| --- | --- | --- |
| 场景 | 断线重连后，服务端按契约重放最近若干条事件；客户端按 `eventId` 幂等/去重 | 重连后 UI 把重放事件当新事件追加 |
| 观察 | 网络层出现重复 `eventId`；UI 条目数不变、无重复条目、计数不翻倍 | UI 条目重复/计数翻倍；或同一操作触发两次副作用（重复提交） |
| 需要的契约 | "允许重放 + 客户端去重/幂等"的来源 | 契约要求唯一/幂等，且未实现 |
| verdict | `PASS`；`counterexamples` 写"网络层重复投递被 UI 去重吸收（契约允许）" | `FAIL`；附 eventId 序列 + UI 条数前后对比快照 |
| 判相反需要 | 证明 UI 真的去重（快照/节点读数），并把"允许重放"的来源写进 `expected_contract` | 证明重复来自重放而非用户重复操作（动作记录 + 请求次数） |

常见误判：只数网络事件条数就写"重复投递=缺陷"。**网络层重复与用户可见重复是两件事。**

## 2. 允许的延迟同步 vs 未收敛缺陷

| | 正常（不判缺陷） | 缺陷（判 FAIL） |
| --- | --- | --- |
| 场景 | 契约写明"最终一致，收敛窗口 ≤N 秒"；多视图在窗口内先后更新 | 契约要求实时/窗口内收敛，但某视图长期不更新或永远不更新 |
| 观察 | t0 视图 A 旧值，t0+2s 更新；视图 B 在窗口内跟上；无报错 | 超出契约窗口仍旧值；或某一视图永不更新；或刷新后才更新（说明未推送） |
| 需要的契约 | 收敛窗口/最终一致的来源 | 实时性要求或收敛窗口的来源 |
| verdict | `PASS`（在 `observation` 记录各视图读取时间与数值） | `FAIL`；附多次读取时间戳 + 网络/事件证据（是否有推送） |
| 判相反需要 | 契约未写窗口 → `INCONCLUSIVE(needs-contract)`，不写"未同步=缺陷" | 排除缓存/读取时间差：至少两次独立读取且间隔超过窗口 |

常见误判：拿"两个视图数字不同"直接判缺陷——先看读取是否同一时刻、契约是否允许延迟。**多视图同步要求由契约决定，不能靠个人印象设定规约。**

## 3. 装饰性闪烁 vs 非预期瞬时变化

| | 正常（不判缺陷） | 缺陷（判 FAIL） |
| --- | --- | --- |
| 场景 | 设计上就有周期性装饰动画（呼吸灯/加载脉冲/强调动效），声明层与实现一致 | 关键内容区出现非预期瞬时变化；或与声明层不一致 |
| 观察 | 变化周期性、幅度/颜色与设计声明一致、不影响文字可读性 | 关键文本/金额/操作按钮区域短时不可读或明显错位；变化不在声明里 |
| 需要的契约 | 设计声明/动画规格（关键帧、时长、循环方式） | 一致的"不应出现该变化"的验收条件 |
| verdict | `PASS` 或"不构成缺陷"（写清依据：声明一致 + 无可见影响） | `FAIL`；必须给出能覆盖该瞬时变化的采样证据（帧 id + 时间窗），或声明层证据 |
| 判相反需要 | 采样覆盖到变化窗口（采样间隔 < 变化时长），否则不能断言"没发生" | 单帧截图不足以证明瞬时变化；需连续帧 + `region` 裁剪 |

红线：**采样没覆盖到，只能写 `INCONCLUSIVE`（INSUFFICIENT_TEMPORAL_RESOLUTION）**；也不能因为"设计上通常有闪烁"就一概不判。

## 4. 静态 WebGL/Canvas 内容 vs 应当变化的渲染故障

| | 正常（不判缺陷） | 缺陷（判 FAIL） |
| --- | --- | --- |
| 场景 | canvas 内容本来就是静态图/一次性绘制；无动画声明 | 声明/契约要求内容随时间变化，但像素恒定 |
| 观察 | 帧间像素稳定、无丢帧；上下文正常；rAF 活跃或空闲都合理 | 声明要求变化，帧间像素恒定；或上下文丢失/报错 |
| 需要的契约 | "静态内容"是设计（无动画声明、验收只要求绘制正确） | "应变化/应重绘"的来源 |
| verdict | `PASS`（静态即正确）；不写"未渲染"，也不写"缺 clear" | `FAIL` 只在"应变化而未变化"且采样足够时成立；机制列为候选，不写死 |
| 判相反需要 | 用 T3 验证某一帧绘制正确（颜色/区域/几何） | 需排除：上下文丢失、采集未覆盖、绘制被遮挡、软件渲染差异 |

反例（错误推理）：像素 3s 不变 + 页面有 canvas → "WebGL 未渲染/缺少清屏"。这是把**观察**直接升级成**机制**；机制必须列候选并用对照实验排除。

## 5. 正常 409 冲突提示 vs 冲突处理缺陷

| | 正常（不判缺陷） | 缺陷（判 FAIL） |
| --- | --- | --- |
| 场景 | 并发修改触发 409；UI 明确提示冲突；资源保持原值 | 409 后 UI 显示成功、资源被部分写入、或没有任何提示 |
| 观察 | 响应 409 + 冲突原因；提示文案出现；重新读取资源仍是旧值 | 响应 409 但提示为成功样式/无提示；或资源出现半更新状态 |
| 需要的契约 | 冲突提示与"不写入"的约定 | 成功/失败反馈与原子性的约定 |
| verdict | `PASS`（三方核对：状态码 + 提示 + 资源终态） | `FAIL`；三方证据缺一不可 |
| 判相反需要 | 用 `network_detail` 看响应体原因、T2 读提示文本、独立读取资源终态 | 只看 toast 或只看状态码都不够 |

## 6. 差异 vs 缺陷：快速判据表

| 现象 | 先查 | 大概率结论 |
| --- | --- | --- |
| 网络层重复 | 契约是否允许重放；UI 是否去重 | 正常（若去重生效） |
| 多视图数值暂时不同 | 读取时间差；契约收敛窗口 | 正常/待确认 |
| 周期性动效 | 设计声明是否包含 | 正常 |
| 静态画面 | 验收是否要求动画 | 正常 |
| 409/冲突提示 | 资源终态是否被改 | 正常（若未写入） |
| 关键内容瞬时不可读 | 采样是否覆盖 + 声明层证据 | 缺陷（证据充分时） |
| 应变化却恒定 | 采样覆盖 + 上下文状态 + 遮挡 | 缺陷或 INCONCLUSIVE |
| 金额/数量与响应字段不符 | 数字来源与字段口径 | 缺陷（有服务端真值时） |

## 7. 反例集：这些写法会被门禁拦下

1. `PASS` + observation 里写"偶尔闪一下但不影响"（第 1 项校验：异常词未解释）。
2. 缺陷清单有 3 条，但只有 1 个 case 判 `FAIL`（第 2 项校验：清单未映射）。
3. 报告写"接口无问题"，证据只有一张 UI 截图（第 3/4 项校验）。
4. 写了"无法观察 opener 关系"，该 case 仍 `PASS`（第 5 项校验）。
5. 截图文件名是订单页，内容却是列表页（第 6 项校验）。
6. 低采样率下写"无闪烁"（应 `INCONCLUSIVE` + 采样不足）。
7. 把"网络层重复投递"直接写成缺陷（未查契约/未看 UI 去重）。
8. 把"像素恒定"直接写成"未渲染"（观察升级成机制）。
